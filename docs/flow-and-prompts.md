## 1. 一句话

- **v0.1（本文 §2 基线）**：Client 状态机 → Host SSE → 扩词 → CLI 双源 → 筛选摘引 → 带证据回答；
  3 次模型调用串行，命中缓存 0 次（v0.1；0.2 见 §11）。
- **v0.2（§11）**：检索后 ② 筛选与 ③ 回答并行；回答按候选编号引用；两边结束后核对，
  缺失引用再触发第 4 次补卡。基础调用仍是 3 次，缓存命中是 1 次（只重跑回答）。

## 2. 端到端时序（v0.1 串行基线，最新见 §11）

```
[Client] 首页输入 / 对话划词
  beginSearch(q) → localStorage: view=results, attempt+1
  Results mount
    有可恢复状态? ──是──> 直接渲染，不发请求
        │否
        └─ EventSource /zsearch/api/stream?q=…        ← 从不带 refresh=1

[Host] loopback 校验 → SSE 头 → 15s keep-alive
  send('query')                                       ← Client 没有监听（死事件）
  searchFor(q, force=false)
    ├─ 进程内缓存命中（key=q.trim().lower，TTL 10min）→ 直接返回整包
    ├─ ① expandQueries()            [LLM-1] 300 tok / 30s / effort off
    ├─ queries = uniq([q, ...variants]).slice(0,4)
    ├─ Promise.all:
    │    collectZhihu: search zhihu  ×≤4（每条 count=10，25s 超时）
    │    collectWeb:   search global ×≤4（同上）
    ├─ 清洗 → 过滤 → dedupe(url)
    │    zhihu: 按赞降序 slice 24
    │    web:   过滤知乎域名/标签页，slice 16（不排序）
    ├─ candidates = [...zhihu, ...web].slice(0,40)
    └─ ② 若 candidates>0：streamText(CURATE) [LLM-2] 2400 tok / 120s / off
           → parseCurationLines → applyCuration（逐字定位/限长/去重/过滤）
           → 失败或 0 条 → heuristicCuration（前 8 条首句）
           → cards ≤ 10
  send('plan') {variants, zhihu, web, candidates, source}
  for card: send('card') ×N（间隔 80ms）
  ③ streamAnswer() [LLM-3] 1800 tok / 120s / effort low → send('answer') ×N
  空输出 → 固定兜底文案
  send('done')

[Client] plan/card/answer/done → 渲染；350ms 防抖写回 localStorage
```

## 3. 逻辑关系

分四层，各自可替换：

1. **UI 状态机**（client.js）
   - `view`: `home` / `results` / `setup`
   - `attempt`（搜索代次）是唯一一致性锚点：换词或重搜时 `attempt+1`，
     旧 SSE 的 `savePanelResults` 会因 attempt 不匹配被丢弃。
   - `started` / `phase` / `interrupted` 决定结果页是"在跑 / 完成 / 中断可重试"。
   - 持久化：`localStorage['dsh-zsearch:panel.v1']`，含 view/query/attempt/cards/answer/plan。
2. **SSE 契约**（host → client）
   - `query`（发了但没人听）、`plan`、`card`、`answer`、`done`、`failure`
   - 服务端串行发；客户端只做累加，不做状态机校验（除 `closed`）。
3. **检索管道**（`searchFor`, index.js:565）
   - 扩词 → 8 路 CLI → 归一化 → 去重 → 排序 → 精选 → 回答
   - 缓存包住整条管道（含 LLM 产物），不是只缓存 CLI 原始结果。
4. **模型层**（`streamText` / `streamAnswer`）
   - 每次调用重新读 `agentDefaultModel.currentSelection()`，不缓存选择。
   - 三处调用互不共享 system 前缀或上下文。

### 降级矩阵

| 失效点 | 当前表现 |
|---|---|
| `llm` / 默认模型缺失 | 扩词 = []（只搜原问）；筛选 = 前 8 条首句（`source:'heuristic'`）；回答 = 固定文案 |
| 扩词超时 / 输出格式漂移 | 静默退化为只搜原问 |
| CLI 检测不到 | SSE `failure`："未检测到 zhihu-cli，请先在引导页安装" |
| CLI 单条查询失败 | `searchOnce` 返回 `[]`，不报错 |
| 筛选输出解析不出 / 0 条 | 走 heuristic 兜底，仍是 8 张卡，`why` 全为"相关结果" |
| 回答为空 | 前端显示"没有拿到模型输出…"兜底 |

### P2 · 证据筛选 + 逐字摘引

| | |
|---|---|
| 位置 | `CURATE_SYSTEM` index.js:435，`curationPrompt` index.js:451，调用点 index.js:585 |
| 触发 | 检索返回且 `candidates.length > 0` |
| 参数 | `maxTokens: 2400`、`timeoutMs: 120_000`、`reasoningEffort: 'off'` |
| 输入规模 | candidates 上限 40（知乎 24 + 全网 16），每条正文截 300 字 → 约 1.2–1.4 万字符。实测单次 `search zhihu --count 10` 返回原文合计 9,663 字符、单条均值 966 字符；截到 300 字后 10 条约 3 千字符 |
| 输出解析 | `parseCurationLines` 只认「可选 # + 数字 + 分隔符 + direct/ecosystem + 分隔符 + 剩余」；分隔符为半角或全角竖线。剩余部分再按第一个竖线切成 quote / why |
| 后处理 | `applyCuration`：quote 必须能 `includes` 命中候选正文（归一化空白+小写）、polishQuote 补句尾、限 26–160 字、按 URL + quote 前 24 字去重、过滤安装命令类文案 |
| 产出用途 | `cards`（≤10），每张 = 原候选元数据 + `quote` + `why` + `relation` |

system（逐字）：

```
你是搜索结果的编辑。用户会给出一个搜索问题，你要从候选里挑出真正能回答它的条目，并为每条摘出 1-2 句原文。
挑选标准：
- 这段话本身就能回答问题的某一部分，或给出关键事实、数据、步骤、结论、一手经验。
- 优先“金句”：信息密度高、可独立读懂、不依赖上下文也能看明白。
- 泛泛而谈、纯引流、只重复标题、和问题无关的，直接丢弃。
摘录规则：
- quote 必须是候选正文里的原文，逐字复制，不改写、不概括、不拼接、不补标点。
- 摘 1-2 个完整句，30-120 字；首尾要落在原文的句子边界上（句号、问号、感叹号之后）。
- 一句话说不完可以连着摘两句，但两句必须在原文里相邻。
- 第一列必须使用候选编号，原样照抄，绝对不要重新编号。
- why 用不超过 20 字说明这句话提供了什么信息（例如“给出三步安装命令”“实测续航 4 小时”）。
- 最多保留 10 条，宁缺毋滥；第一行就是数据行，不要解释、不要复述规则。
输出格式：编号|direct或ecosystem|引用原文|一句话理由
```

${item.text}（cleanText 后已截 300 字）

## 5. 三个 Prompt 的关系

```
query ──P1──> 检索式 ──CLI──> 候选(≤40) ──P2──> 证据(≤10 条 quote) ──P3──> 回答
```

- 单向串联，后一步只看到前一步的产物，没有回环。
- **P3 看不到候选正文**，只看到 P2 摘出的 1–2 句 → 回答质量的上限由 P2 决定。
- 三个 prompt 不共享 system 前缀、不互传上下文、没有任何 few-shot 示例。
- 编号语义：P2 的编号是候选序号；`applyCuration` 重排后，P3 用 1..N，客户端按 `cards[n-1]` 对齐。
- 三处都覆盖了 profile 的 `reasoningEffort: max`（P1/P2 off、P3 low）。

## 6. 优化点（按收益排序，本次未改代码）

### P2 是投入产出比最高的一处

1. **两个字段是纯浪费**：`why` 和 `relation` 写进了 card，但 `client.js` 全文没有读取
   （卡片只渲染 quote/作者/标题/互动数）。第四列和 `direct/ecosystem` 分类既不展示，也不参与排序。
   要么删掉这两列（缩短输出、减少格式漂移），要么在 UI 上真正用起来（例如卡片显示 `why`、按 relation 排）。
2. **分隔符与内容冲突**：quote 里出现 `|` 会被 `parseCurationLines` 当成字段边界 → quote 被截成半句；
   截断后要么长度不达标被丢，要么带着半句话通过校验。输出改成 JSON（或 `<<< >>>` 包裹）更稳，解析失败再回退旧格式。
3. **提示词长度和代码校验不一致**：prompt 说 30–120 字，`applyCuration` 收 26–160 字。
4. **候选正文先截 300 字**：模型只能在这 300 字里摘；原文靠后的好句子永远摘不到。
   可以做两段式（先只给标题+首 120 字挑 15 条，再给全文摘引），或把截断放到 500 字。
5. **候选排序不是相关性**：知乎按赞排序（热榜旧答案挤掉相关的冷门新答案），全网不排序。
   可以按"与 query 的词面重合 + 赞数 + 来源位置"重排后再喂给模型。
6. **40 条输入偏大**：输入约 1.2–1.4 万字符；2400 输出 token 对 10 行中文够用，但格式一漂就整批走 heuristic。
   先做规则预筛（去空、去纯标题重复、同站最多 2 条）可以把候选压到 24–28 条。
7. **无重试/修复轮**：解析失败直接丢给 heuristic，等于白花一次 2400 token 的调用。

### P1 可以更省、更准

1. 扩词是检索前的**串行**模型调用，直接加首屏延迟；短查询或高置信查询可以跳过。
2. "至少一条用英文"对知乎源基本无效（知乎是中文内容），只对 global 有用；
   而 global 里的知乎域名又会被过滤。按来源分别生成检索式更合理。
3. 没有示例、没有实体/时间约束；输出靠行解析，模型加编号时靠正则兜底，加了引号或前缀说明就会混进检索式。
4. `variants` 已随 `plan` 下发，但 UI 完全不显示，无法观察扩词质量。

### P3 的约束

1. 200–500 字对"怎么选/怎么装"够用，对需要对比、步骤、边界条件的问题偏短。
2. 只给 quote 不给上下文，容易出现断章取义；prompt 只说"证据不足要说"，没说证据冲突怎么办。
3. 数据里没有任何时间字段（知乎条目只有赞/评论），问"最新/2026"时模型无从判断。
4. `reasoningEffort: 'low'` 覆盖了 profile 的 `max`，是否跟用户默认走值得定。
5. 引用越界不校验：模型写出 `[11]` 时客户端仍渲染可点击角标，但 tooltip 退化成"来源 11"、没有对应卡片，也不报错。

### 管道与可观测性

1. **`refresh=1` 是死参数**：服务端支持，但客户端从不发送 → "重新检索"/↻ 在 10 分钟内拿到的是缓存包
   （包括上次的 cards 和 answer），不是新检索。是"省成本"还是"行为缺陷"，需要产品上定。
2. 缓存 key 只有 query，不含模型/配置；换模型后 10 分钟内仍是旧结果。
3. 同一 query 并发（两个面板/两次点击）不合并，会重复跑两遍完整管道。
4. 没有 token / 耗时日志；`plan.source`（llm / heuristic）、`variants`、`candidates` 都已下发但 UI 不显示，
   DEBUG 菜单也没接。
5. 客户端断开后 `searchFor` 不会取消（LLM、CLI 继续跑完）；流式回答只 `break` 不 `abort`。

## 7. 如果开始优化，建议顺序

1. **先定 P2 的输出契约**（删 `why`/`relation` 或改成 JSON）——改一处，解析稳健性和 token 都受益。
2. **再做候选预筛/重排**——不改 prompt 也能提质量，且能缩短 P2 输入。
3. **最后调 P1/P3 的措辞与 effort**——需要跑几组 query 对比，收益最依赖评测方式。

需要评测口径的话，建议先记录每次检索的：扩词条数、候选数、LLM 采纳数、heuristic 回退率、首字延迟、总延迟。

## 8. 2026-11-13 Prompt 优化（已改代码，原版备份 `docs/.index.js.before-prompt.bak`）

> 本节覆盖上文 §4 中 P2 / P3 的逐字内容；最新原文以 `index.js` 的 `CURATE_SYSTEM`、`ANSWER_SYSTEM` 为准。

### P2 筛选：从“挑相关条目”改成“挑金句”
- 写明金句的五种类型：A 鲜明判断、B 硬信息、C 可执行、D 一手经验、E 洞见。同时列出反例：开场客套、“看情况”式空话、反问句、营销导流、指代不明的句子。
- 要求按对读者的价值排序，覆盖不同角度，同一观点只留一条，并要求兼顾知乎与全网两类来源。
- 输出格式改为 `编号|标签|原文`。原文放在最后，所以原文里出现 `|` 也不会被截断（修复了 §6-2 的问题）。删除了没有实际用途的 `direct/ecosystem` 字段；`标签`（2–8 字）改为在卡片上显示（`.zs-tag`）。解析时仍兼容旧格式。
- 加了两行输出示例。字数要求统一为 20–100 字，代码校验相应放宽到 18–150 字（修复了 §6-3 的不一致）。
- 候选的元信息中加入内容类型和答主身份（authorTag），方便模型识别一手经验。

### 候选预处理（不涉及模型）
- 丢弃正文少于 30 字、或正文与标题相同的候选。
- 排序规则：与检索式的词面重合度（中文按二字词计算）×3，加上 log(赞同数)×0.6。原来只按赞同数排序，旧的高赞答案会挤掉相关的新答案（修复了 §6-5）。
- 同一个全网站点最多保留 2 条。候选上限从 40 条（知乎 24 + 全网 16）改为 32 条（知乎 20 + 全网 12），每条正文截断从 300 字放宽到 420 字（缓解 §6-4、§6-6）。

### P3 回答：给出固定结构，要求有观点、好读
- 固定结构：开头 1–2 句直接给结论，关键判断加粗；正文用 2–3 个 `##` 小标题，按问题类型组织（怎么做 / 怎么选 / 是什么 / 值不值）。证据里有一手经验时，单独设一节「知乎上怎么说」，作为区别于普通搜索的特色。证据有分歧时写明分歧，证据不全时说明缺什么。
- 可读性：总长 250–600 字，每段不超过 3 句，列表项以加粗短语开头，禁用套话，数字按原文照写。
- 引用：角标放在句末标点之前，可以连写 `[1][3]`。
- 证据里除金句外，还提供卡片正文前 160 字作为上下文，减少断章取义（缓解 §6 中 P3-2 的问题）；元信息加上答主和内容类型。`maxTokens` 从 1800 提高到 2200。

### 未改动
- P1 扩词、缓存、`refresh=1` 等管道问题。
- `market/` 里同名的 prompt。

## 9. 2026-11-13 回答区 Markdown 与排版

### 渲染器（`client.js` 的 `renderInline` / `renderAnswer`）
修改前，回答区的渲染器只支持段落、`#` 标题、单层 `-` / `1.` 列表，以及行内的 `**粗体**`、`` `代码` ``、`[n]` 和链接，存在以下问题：
- 粗体里的角标 `[n]` 不会被识别；
- 有序列表中间插一段续行，编号会重新从 1 开始；
- 嵌套列表会被拍平成同一级；
- 引用块、表格、分隔线、`*斜体*`、`__粗体__` 都会原样显示成符号；
- 流式输出时，只收到一半的 `**` 会把星号闪现出来。

现已补齐：
- 行内元素可以嵌套，粗体里的角标也能识别和点击；
- 有序列表保留原起始编号（`start`）；
- 列表支持缩进续行和一层嵌套（`.zs-sub`）；
- `###` 渲染为 h3；
- 支持引用块、分隔线和 GFM 表格；
- 流式输出时，未闭合的 `**` 自动补全，行尾多出来的 `**` 直接去掉。

### Prompt
在 `ANSWER_SYSTEM` 中新增【Markdown 规范】，把可用写法限定在渲染器支持的子集内：
- 块之间空一行；每段不超过 3 句、约 120 字。
- 小标题只用 `##`，4–10 字，内容概括本节结论。
- 列表项统一写成「`- **短语**：解释`」；有先后顺序的步骤用 `1.`；最多嵌套一层。
- 加粗：开头段 1–2 处，其余每段或每个列表项最多 1 处。
- 禁用表格、引用块、代码块、分隔线、emoji，结尾不写「总结」小节。

渲染器虽然已经支持表格和引用块，但只作为兜底，prompt 里仍然禁用它们。

## 10. 2026-11-13 右侧证据：视角分组

参考了 mino 的内容发现 Demo，用到的材料：
- `workspace/0729-综搜主题内容拓展/02-动态Demo/src/llm.js` 中的 `DISCOVERY_PROMPT_V5`；
- 同目录 `prompts/grouping-user-questions-v6.js`；
- `workspace/0225-zhihu-aisearch-探索模式/0309-ai_explore_interactive/grouping-prompt-v5.md`（“老炮朋友”版）；
- 对 v3→v4 的复盘：规则越多效果越差，靶心是“挖料，不给骨架”。

### 借鉴了什么
- 定位：“不是做分类，而是帮用户发现最值得继续看的问题”（V6）；用懂行朋友的口吻，在用户要的方向上挖深一层（v5）。
- 顺序：先读结果再定分组，不要先编问题再找内容去填（V5）。
- 反例：避开“起因·经过·结果”这类百科骨架；保留了四平之战的 before/after 例子（v4/v5）。
- 每组用用户自己的话写一个问题，配一个 2–4 字的短标签；各组彼此独立，意思重叠的合并；同一条结果只进一组；挖料，不编料。

### 没照搬的
- 没用 JSON schema。沿用逐行格式，每组可以边生成边解析，原文里出现 `|` 也不会截断；同时兼容两种旧格式。
- 没有 emoji、meta、pullquote 字段。我们的卡片本身就是金句，不需要单独的 pullquote。
- 组数按右栏的容量缩小：2–4 组，每组 2–4 条，总数不超过 12 条（Demo 是 3–6 组，每组 3–12 条）。

### 输出格式与渲染
- 模型输出格式：
  - `主题|大问题`
  - `组|标签|问题`
  - 后面跟若干行 `编号|原文`
- Host 处理：
  - 主题写入 `plan.topic`；
  - 每张 card 带 `group: {label, question}`，并同时传给左侧回答作为「视角」；
  - `MAX_CARDS` 从 10 改为 12。
- Client 渲染：
  - 顶部显示「引用证据 · N 种视角」、大问题标题，以及每组一个跳转 chip；
  - 每组的组头是渐变序号 + 标签 + 问题 + 条数，组内仍用原来的分享卡片做瀑布流；
  - 卡片编号保持全局顺序，与左侧 `[n]` 角标对齐。
- 回退：没有分组信息时（启发式兜底、旧缓存），回到原来的「引用证据」单流布局。

原版备份：`docs/.index.js.before-grouping.bak`、`docs/.client.js.before-grouping.bak`。

## 11. 2026-11-15 并行筛选 + 引用核对

### 为什么改
筛选（②）和回答（③）原来是串行的：③ 只看到 ② 选出的 ≤12 条金句。改成并行后，左栏能更早出字，但 ③ 看不到 ② 的结果，必须自己处理「回答引用的候选没有对应卡片」。

### 新契约
- 候选生成时分配 `candidateId`（1..N），② 和 ③ 共用同一份编号。
- ③ 的输入从「≤12 条金句」改为「≤32 条候选正文」，引用写成 `[候选编号]`。
- ③ 与 ② 并行；② 完成后本地校验得到 `cards`，③ 完成后从回答里抽出引用编号。
- 对每个引用编号：先按 `candidateId` 找卡，再按 URL 找卡；都没有的进入 `missing`。
- `missing` 非空时做一次批量摘句（`BACKFILL_SYSTEM`），把结果标成 `backfill: true`，分组为「其他参考内容」，按首次引用顺序追加到右栏末尾。
- 最后下发 `citations` 事件（候选编号 → 显示序号），再下发 `done`。客户端在 `citations` 到达前把未解析的角标显示为「加载中」，到达后仍缺失的显示为不可点的灰色编号。

### SSE 事件变化
`query` → `plan`（先发，`topic` 可能为空）→ `topic`（② 完成后）→ `card`×N → `answer`×N（与卡片交错）→ `card`×M（补充）→ `citations` → `done`。

### 缓存
- 缓存只在 ② 完成后写入，包含：候选、卡片、主题、来源。
- 命中缓存时跳过扩词、CLI 检索和 ②，但仍会重新跑 ③（回答不缓存），再按引用核对；所以命中缓存是 1 次模型调用，不是 0 次。
- 缓存最多 40 条；超出后按插入顺序淘汰最早的一条。

### 代价与已知限制
- ③ 的输入从约 3 千字符涨到约 1.3 万字符（32 条 × 420 字），回答调用更贵、可能更慢；并行省下的是 `min(②, ③)`。
- 左栏句子和右栏金句不再保证逐字同源：③ 基于候选原文写，右栏展示 ② 摘的句子；「其他参考内容」缓解但不消除这个差异。
- 补充摘句失败时先用本地首句兜底；兜底也校验不过，该角标保持灰色不可点，不会指向错误卡片。
- `citations` 之前的角标是「加载中」样式；如果客户端在这之前断开，恢复后的面板会按已保存的 `citationMap` / `citationsFinal` 重建。
